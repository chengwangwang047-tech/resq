# ResQ Day24 — 性能压测与并发正确性报告

**项目：** ResQ 共享计算资源预约与任务调度平台  
**实验日期：** 2026-10-22  
**测试工具：** k6、JDK jcmd、Redis、MySQL  
**测试范围：** GET 查询性能、POST 预约并发竞争、Redis 缓存性能

## 1. 实验目标

本次实验主要验证四个方面：

1. GET 时隙查询接口在不同虚拟用户负载下的响应时间和稳定性。
2. POST 预约接口在多人竞争同一时隙时，能否避免超卖。
3. Redis Cache Aside 是否减少 MySQL 时隙查询，并改善响应时间。
4. 当接口出现异常长尾延迟时，能否利用真实监控和 JVM 线程快照定位问题。

本实验不以证明生产环境最大 QPS 为目标。

## 2. GET 时隙查询压测

### 2.1 测试条件

- 接口：`GET /api/resources/111/slots?date=2026-10-25`
- 工具：k6
- 并发档次：50、100、200 VU
- 每档持续：30 秒
- 每次迭代包含 `sleep(1)`
- 返回校验：HTTP 200，并且时隙结果非空
- 控制高频 DEBUG 日志输出，避免日志 I/O 干扰

### 2.2 测试结果

| 指标 | 50 VU | 100 VU | 200 VU |
|---|---:|---:|---:|
| 请求数 | 1,500 | 3,000 | 6,000 |
| 实际 req/s | 47.53 | 94.95 | 189.55 |
| 平均响应 | 5.38ms | 5.97ms | 6.55ms |
| P95 | 9.44ms | 10.46ms | 14.68ms |
| P99 | 10.77ms | 23.34ms | 24.25ms |
| 最大耗时 | 11.42ms | 28.21ms | 31.63ms |
| HTTP 失败率 | 0% | 0% | 0% |
| 内容检查通过率 | 100% | 100% | 100% |

数据来自当天用户实际粘贴的 k6 输出，尚未在本报告编制过程中重新读取本地原始文件。

### 2.3 结果分析

从 50 VU 增加至 200 VU，请求速率接近按比例增长，平均响应时间仅由 5.38ms 增加至 6.55ms。

200 VU 下，P99 为 24.25ms，6000 次请求无失败。

说明在该本地测试条件下，GET 时隙查询表现稳定，未观察到严重的负载退化。

**实验限制：** 脚本中的 `sleep(1)` 主动限制了请求频率，因此 189.55 req/s 并非系统最大吞吐量。VU 数量也不等于服务器始终同时处理的 HTTP 请求数量。

## 3. POST 预约并发竞争实验

### 3.1 测试设计

接口：`POST /api/reservations`

实验编号：`d24_20261022_182544_3163fc`

每个档次使用独立的实验时隙，所有时隙在测试前均为 AVAILABLE，且没有预约记录。

- 50 VU：测试时隙 117
- 100 VU：测试时隙 118
- 200 VU：测试时隙 119

共准备 200 个独立测试用户，每个 VU 使用自己的 JWT 和不同的 `X-Request-Id`。

每个 VU 只发送一次新的预约请求，通过共同的未来时间屏障尽可能集中发起竞争，不重复提交、不绕过业务限流。

### 3.2 测试结果

| 指标 | 50 VU | 100 VU | 200 VU |
|---|---:|---:|---:|
| 总请求数 | 50 | 100 | 200 |
| 创建成功 201 | 1 | 1 | 1 |
| 库存冲突 409 | 49 | 99 | 199 |
| 限流 429 | 0 | 0 | 0 |
| 其他状态 | 0 | 0 | 0 |
| P95 | 639.30ms | 332.58ms | 596.67ms |
| P99 | 647.52ms | 345.06ms | 616.79ms |
| 技术失败率 | 0% | 0% | 0% |
| 有效预约数（前→后） | 0→1 | 0→1 | 0→1 |

三个档次共发送 **350 次预约请求**，得到 3 次成功创建、347 次预期库存冲突。

所有 409 均经过响应内容核对，属于时隙不可用的业务冲突，而非服务器技术故障。

### 3.3 数据库正确性验证

对三个测试时隙分别执行只读数据库核验：

- 测试前：AVAILABLE，有效预约数为 0。
- 测试后：RESERVED，有效预约数为 1。
- 没有发现同一时隙产生多条有效预约。

核验有效预约的 SQL：

```sql
SELECT COUNT(*) AS effective_count
FROM reservation
WHERE slot_id = 117
  AND status IN ('PENDING', 'CONFIRMED');
```

其他两档分别使用 slotId 118、119。

### 3.4 并发正确性机制

当前 ResQ 的并发控制采用：

**Redisson 时隙锁 → MySQL 事务 → 条件 UPDATE → 创建预约记录**

MySQL 条件更新负责确保只有符合 AVAILABLE 条件的时隙能够被占用，分布式锁用于协调并发请求。

当前预约表没有针对 `slot_id` 的有效预约唯一约束，不能把本次结果描述成由该唯一约束保证。

**结论：** 在本次 50、100、200 VU 的单时隙竞争实验中，没有观察到超卖。

**限制：** 每档只有一次短脉冲竞争，成功写入样本每档仅有一个，P95/P99 主要反映业务冲突路径，不代表持续成功写入吞吐能力。200 VU 档依据现有客户端时间戳，保守确认同时在途峰值为 198。

## 4. Redis 缓存性能对照实验

### 4.1 实验设计

实验编号：`d24cache_20261022_185550_9afb96`

使用隔离 MySQL 数据库、Redis DB15 和独立 RabbitMQ vhost，运行未修改的 ResQ 应用代码。

实验创建一个专用计算资源及 12,240 条时隙数据，每个日期恰好包含两条时隙。

测试接口为带日期的 GET slots。

比较两条业务路径：

**Hot：热缓存命中**

Redis 已存在该日期的时隙缓存 Key，请求直接使用缓存结果。

**Cold：首次缓存未命中**

Redis 缺少该日期的时隙 Key，请求查询 MySQL，再将结果回填 Redis。

为了保证每次 Cold 请求确实未命中，测试使用大量独立日期，使每个请求对应不同的 Redis Key。

资源详情缓存层在两组中均保持热状态，比较重点为时隙缓存层。

### 4.2 主要结果

每档每组两轮，合计 **42,000 次 HTTP 请求**。

| VU | 路径 | 请求数 | 平均耗时 | P95 | P99 |
|---|---|---:|---:|---:|---:|
| 50 | Hot | 3,000 | 4.96ms | 8.71ms | 10.49ms |
| 50 | Cold | 3,000 | 8.33ms | 14.13ms | 19.58ms |
| 100 | Hot | 6,000 | 4.73ms | 9.07ms | 23.83ms |
| 100 | Cold | 6,000 | 7.41ms | 13.57ms | 36.19ms |
| 200 | Hot | 12,000 | 4.48ms | 8.91ms | 23.40ms |
| 200 | Cold | 12,000 | 7.62ms | 16.45ms | 22.12ms |

所有请求的 HTTP 和业务内容检查均通过，失败率为 0%。

### 4.3 平均响应时间改善

以 Cold 组为基准：

| VU | 热缓存平均延迟降低 |
|---|---:|
| 50 | 40.4% |
| 100 | 36.2% |
| 200 | 41.2% |

平均响应时间在三个档次中均明显降低。

P95 也均有所改善，但 200 VU 主实验中 Hot 的 P99 略高于 Cold，不能认为 Redis 缓存使每项长尾指标必然改善。

### 4.4 Redis 与 MySQL 证据

以已核验的一轮 200 VU、6000 次请求为例：

| 证据 | Hot | Cold |
|---|---:|---:|
| 时隙 Redis GET | 6000 | 6000 |
| 时隙 Redis SET | 0 | 6000 |
| 时隙 MySQL 查询 | 0 | 6000 |
| MySQL 返回时隙行数 | 0 | 12000 |

因此，Hot 组在该实验中避免了时隙 MySQL 回源查询。

实验采用 Redis 键状态、命令观测、数据库连接级查询计数和返回行数交叉验证。

有一次 50 VU 冷组的共享 SQL digest 仅统计到 1498 次，而其他证据对应 1500 次。该轮及配对热组未纳入主表，原始记录保留，未人为修正数字。

### 4.5 关闭 Redis MONITOR 后复测

为减少 Redis MONITOR 带来的额外观测开销，进行了单独的 200 VU 对照。

| 指标 | Cold | Hot |
|---|---:|---:|
| 请求数 | 6000 | 6000 |
| 平均耗时 | 6.57ms | 4.16ms |
| P95 | 13.17ms | 8.50ms |
| P99 | 17.29ms | 15.91ms |
| HTTP / 业务失败率 | 0% | 0% |

关闭 MONITOR 后，热缓存路径仍具有更低的平均响应时间和 P95，本轮 P99 也更低。

### 4.6 缓存实验结论与边界

**核心结论：** 在本地隔离、每日期两条时隙、受控请求节奏下，Redis 缓存命中比首次未命中、MySQL 回源并回填的路径具有更低的平均响应时间，同时减少了 MySQL 时隙查询。

但本实验未关闭 Redis 缓存，也没有测试磁盘冷读。Cold 组仍正常使用 Redis GET 和 SET，只是时隙 Key 在首次访问时不存在。

不能把两组差值全部归因于 MySQL 本身的执行耗时，也不能据此推断生产环境容量。

## 5. 性能异常排查：Logback 日志输出竞争

### 5.1 异常现象

在早期 GET 压测中，50 VU 曾出现多个请求同时等待几十秒的现象。

一次异常轮次中，平均响应时间约 7.78 秒，P95/P99 约 48.62 秒。

随后使用 curl 交叉验证，发现同一时间段普通 HTTP 请求也可能超时，排除了仅由 k6 统计显示造成异常的简单解释。

### 5.2 JVM 线程快照

通过 `jps -l` 找到 ResQ JVM，再使用 `jcmd <PID> Thread.print -l` 抓取快照。

正常状态的线程状态统计：

| 状态 | 数量 |
|---|---:|
| RUNNABLE | 44 |
| WAITING | 30 |
| TIMED_WAITING | 11 |

异常状态：

| 状态 | 数量 |
|---|---:|
| RUNNABLE | 45 |
| WAITING | 70 |
| TIMED_WAITING | 11 |

正常快照中包含 Logback `OutputStreamAppender.writeBytes` 的调用栈计数为 0，异常快照中为 51。

进一步分析发现：

- 某个 Tomcat 工作线程在执行 `ResourceSlotCache.get()` 的 DEBUG 日志时，停留于 Logback 的控制台写入调用路径。
- 其他线程在 Logback `OutputStreamAppender` 的 `ReentrantLock` 上等待。

说明异常时存在显著的同步日志输出竞争。

### 5.3 处理与结果

通过临时运行环境调整日志级别，减少高频 DEBUG 控制台输出，不修改业务逻辑。

后续 50 VU 测试恢复为低毫秒级响应，并完成 100、200 VU 测试，没有在这些轮次中再次观察到数十秒集体卡顿。

**结论：** 同步日志输出是此次性能异常的强嫌疑因素，线程快照提供了直接的锁竞争证据，减少 DEBUG 输出后性能明显改善。

**限制：** 尚未通过严格重复的开关对照证明它是唯一根因，不排除终端 I/O、运行环境调度等其他因素。

## 6. 综合结论

本次 Day24 验证了：

1. **查询性能：** GET slots 在 50、100、200 VU 的带休眠固定负载下，保持较低响应延迟且 HTTP 请求全部成功。
2. **并发正确性：** POST 单时隙竞争中，每档恰好一个请求成功创建预约，其他请求发生预期库存冲突，没有观察到超卖。
3. **缓存效果：** Redis 热命中路径在三档测试中的平均延迟比首次 miss 回源路径降低约 36%～41%，并显著减少 MySQL 时隙查询。
4. **故障排查：** 利用 k6、curl 和 JVM Thread Dump，发现同步控制台日志竞争与严重长尾延迟之间的关联。

这些成果分别验证了性能、业务正确性以及问题排查能力，不能用单一 QPS 或 P99 数字替代全部结论。
